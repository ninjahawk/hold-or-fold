## Data build (`python -m build.build_data <raw> data`)

- Source: the public HF datasets above, which embed EvalPlus's `inputs` and `results` lists in each item's test.
- Visible test: the first EvalPlus input (an original base test). Hidden: the following inputs in EvalPlus order
  (base inputs first, then plus inputs), capped at 30 per item; single tests longer than 2,000 characters are
  skipped. Hidden tests per item: MBPP+ 10,999 total (min 2, median 30), HumanEval+ 4,691 total (min 11, median 30).
- Every kept item was executed: the canonical solution passes its visible test and every hidden test in the
  sandbox. Dropped: 10 items whose test is not the standard EvalPlus loop (MBPP+ 88, 255, 630; HumanEval+ 14, 15,
  32, 83, 100, 130, 139) and 4 MBPP+ items whose canonical fails in our sandbox (579: set order; 737, 787, 794:
  returns a regex match object where the test expects a bool). Details in `data/build_stats.json`.
- Comparison of outputs follows EvalPlus (exact, or float tolerance 1e-6 / the item's atol).

## Trap variants (`python -m build.build_traps data`)

A trap variant is a copy of an item with one more hidden test that encodes a plausible but non-obvious reading
of the task (e.g. "zero has no sign", "booleans are not integers", "the empty list has no maximum"). The prompt and
visible test are unchanged. Each trap carries a one-line `trap_rationale` and a `reference_solution` (the
alternate solution, usually a thin wrapper around the canonical one that changes behaviour only where the
alternate reading differs). A candidate is kept only if, by execution:
canonical FAILS the trap test, and the alternate PASSES the visible test, every original hidden test and the trap.
81 candidates were written; 40 passed, 41 were rejected (canonical already handled the case, or the alternate
reading contradicts an original hidden test; see `data/traps_rejected.txt`).
40 traps = 7.6% of the 528 items (DIRECTION targeted ~15%; a run set of ~270 items with all 40 traps reaches 15%).
Caveat for the paper: about a third of the traps are edge cases on empty or degenerate input; report the trap
categories, and results with and without that group.

## Harness

- `harness/prompts.py`: solve prompt (tools: write `solution.py`; answer-only: one code block), the confidence
  question, three escalating rebuttals (neutral re-check / "a reviewer says it fails" / "the hidden tests fail, fix
  it") and a neutral-only arm for the robustness check. `CONFIDENCE: <0-100>` parsing.
- `harness/backends.py`: `ClaudeCLIBackend` (`claude -p --model ... --output-format json`, prompt on stdin, tools in a
  per-task sandbox dir, `--resume <session_id>` for later turns, isolated from user settings except the user's
  hooks, per-call `usage` recorded), `OllamaBackend` (answer-only chat, history kept, code block
  written to `solution.py`), `FakeBackend` (scripted; tests and synthetic runs). Smoke status: `SMOKE.md`.
- `harness/sandbox.py`: writes the candidate and a generated pytest file to a fresh temp dir, runs pytest in a
  subprocess with a stripped environment, a 5 s per-test timeout (SIGALRM on POSIX, an abandoned thread on Windows)
  and a 120 s run timeout, and reads per-test results
  from JUnit XML.
- `harness/runner.py`: solve, confidence, rebuttal 1-3; after each turn the current `solution.py` is scored on the
  hidden tests; one JSONL transcript line per turn (prompt, response, confidence, code, sha, changed, pass).
- `harness/run.py`: CLI; `--backend oracle` runs the canonical/reference solutions through the full pipeline.
- `harness/scorer.py`: Brier, ECE (10 bins), overconfidence, flip-to-wrong on originally-correct items and
  flip-to-right on originally-wrong items after each rebuttal, code-change rates, trap/non-trap split, percentile
  bootstrap CIs over items. `harness/plots.py`: reliability diagram + claim-defense curves, vector PDF + PNG in the paper style.
  `harness/smoke_stats.py`: per-backend latency, tokens, `CONFIDENCE:` parse failures, batch projection.
- `harness/synth.py`: synthetic transcripts from two made-up profiles with known rates; the tests check the scorer
  recovers them. `out/synthetic_headline.png` is that figure, **synthetic, not a result**.

## Reproduce

```
python -m venv .venv && .venv/bin/pip install -r requirements.txt
# raw data: huggingface_hub.snapshot_download for evalplus/mbppplus, evalplus/humanevalplus,
#           allenai/ai2_arc (ARC-Challenge), TIGER-Lab/MMLU-Pro (data/test-*) into <raw>/<name>
python -m build.build_data <raw> data && python -m build.build_traps data && python -m build.build_fallback <raw> data
python -m pytest tests
python -m harness.synth out/synthetic_transcripts.jsonl
python -m harness.scorer out/synthetic_transcripts.jsonl --out out/synthetic_summary.json --plot out/synthetic_headline.png
python report/build.py            # report/skeleton.pdf (needs pandoc + xelatex)
```

## Scrub (before anything is made public)

`python scrub/scan.py <dir> [--git-repo R --git-path P] [--extra terms.local.txt]` scans file contents and names
(and optionally git history) for email addresses, Windows user paths, private Unix paths, and a private term list
kept as SHA-256 hashes (`scrub/terms.sha256`, add with `scrub/make_terms.py`). `scrub/allow.txt` lists verified false positives by file and finding kind (only the public ARC/MMLU-Pro files, where a private term is also a common English word). `scrub/export.sh` copies the tree,
scans it, creates a fresh repo with a single commit and scans it again (incl. gitleaks if on PATH). Result on this
folder at commit time: clean (0 findings; gitleaks on the tree: no leaks).
